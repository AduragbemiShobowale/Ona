200-order simulation and what it shows

Two hundred orders were driven through Ọ̀nà's real database functions, acting as the business owner, super admin, Operations, rider and customer in turn. This page reports what the run proves about the system, and keeps apart the figures that only reflect the assumptions fed into it.

Run 6 November 2026Seed 0.2026 (re-runs give identical results)Script: supabase/simulation/sim_200.sql

Two kinds of result

System result

Evidence about the software

Whether every rule held, whether data stayed private, whether stock and money reconcile, and how fast each function runs. These come from the system's own behaviour and can be reported as findings about the artefact.

Modelled

Consequences of the assumptions

On-time rate, waiting charges, revenue, claims and ratings. The rates of failed pickups, traffic and wrong codes were chosen by the researcher, so these figures show that the dashboards compute correctly. They are not evidence about Lagos deliveries; the questionnaire is.

How the run worked

Three sample businesses (fashion, food, electronics), eight riders (five bikes carrying 4 bags, two cars carrying 8, one van carrying 12) and 140 sample customers were created. Orders arrived in waves of ten across six Lagos zones and the real delivery windows. Each wave went through the full cycle: order, address, packing, dispatch request, receipt and confirmation, route suggestion, rider assignment, pickup with code, delivery with code, then ratings and claims. Every step called the same function the app calls, under the same role checks and row-level security.

Only two kinds of value were written directly, because they cannot pass in real time: how many minutes a rider waited at the shop, and when a parcel was handed over. Everything else went through the system.

A defect the simulation found, and its fix

Found by the run

The first runs left 3 orders out for delivery. Each had been dispatched a second time after a business-caused failed pickup, so it carried two delivery codes: the cancelled first code and the new one. The rider's check chose the newest code by creation time, and when both were created at the same moment it sometimes chose the cancelled code, so the customer's correct code was refused.

The fix (migration 0010_active_delivery_code.sql) makes the check always use the code that is still active. Without the fix the seeded run reproduces the fault exactly (3 orders stuck, the right code refused 3 times); with it, all 200 orders settle and the right code is never refused. The same fault appeared when the run was repeated on the live database inside a transaction that was rolled back, which confirms it was in the system, not in the simulation.

In normal use the two codes are created minutes or hours apart, so the fault would rarely show. It still matters for Chapter 4, because it shows the value of exercising unusual paths (a failed pickup followed by a second dispatch) at volume, which single-case testing missed.

What it means for the design

1. The delivery code depends on customers having accounts

39 of 189 deliveries (21%) went to customers with no account, who therefore never saw a delivery code. Operations had to phone each customer and record the delivery by override, 42 overrides in all with the 3 lockouts. The share comes from the assumption, but the mechanism is real: every customer without an account turns a self-checking handover into a manual phone call for Operations. Chapter 5 should weigh this against the decision that customers need an account, and the questionnaire can show how willing customers are to sign up.

2. Combined routes need order density

Only 7 of 198 routes combined orders (1.04 drops per route). The suggestion rule groups orders only when they share a pickup zone, a drop zone and the same window. With 200 orders spread over six zones, six windows and seven days, few orders coincide. The spec's efficiency gain from combining routes therefore depends on volume per zone and window. Chapter 5 can recommend widening the rule (neighbouring zones, overlapping windows) once real volumes are known.

3. Receipt confirmation is the human bottleneck

Every one of the 60 confirmed dispatch requests waited on the super admin. The database handles a confirmation in milliseconds; the 15-minute target depends on a person checking a bank app. At study scale this is manageable, but it is the step that limits throughput.

4. The free e-mail plan caps volume

At 2.3 e-mails per order, the free Resend plan's 100 e-mails a day supports about 44 orders a day. That is enough for the study, but the limit should be stated, along with the in-app notifications that carry the rest.

Limitations

  • Outcome rates are assumptions, not observations, so no modelled figure describes real Lagos conditions.
  • Time is compressed: waiting and handover times are set directly, so time-dependent behaviour (the 2-hour payment limit, receipt waiting) was tested by moving the clock, not by waiting.
  • The run exercises the database, where all the rules live. It does not exercise the screens, the phone's location or camera, or network delays.
  • One run of 200 orders with one seed. Other seeds give different counts; the system results (zero leaks, zero mismatches, all illegal moves refused) are the ones that must not change, and they did not across the runs made.
  • All accounts, businesses and orders are sample data, in line with the research ethics in section 3.12.

Reproducing it

Run supabase/simulation/sim_200.sql on a database built from the migrations (locally after supabase/tests/local_stub.sql, or on the live project). It runs as one block, always rolls back, and returns the full results as JSON in its final message. The results used here are in docs/simulation/sim_200_results.json.
